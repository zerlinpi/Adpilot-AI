## 4. ⚠️ CRITICAL — `listing_quality_checks` dual-entity collision (flagged for user)

**Two entities map to the same table `@Table(name = "listing_quality_checks")`:**

| Entity | Module | `issues` / `recommendations` mapping |
|---|---|---|
| `review/entity/ListingQualityCheckEntity.java` | review | `@JdbcTypeCode(SqlTypes.JSON)` + `columnDefinition = "json"` |
| `listingops/entity/ListingMonitorEntity.java` | listingops | `columnDefinition = "TEXT"` (no `@JdbcTypeCode`) |

### What V1 defines
```sql
issues JSON DEFAULT (JSON_ARRAY()),
recommendations JSON DEFAULT (JSON_ARRAY()),
```
All other columns (id, store_id, asin, sku, the six `*_score DECIMAL(5,2)`, checked_at,
created_at) are **identical** between the two entities and **match V1**.

### The conflict
The two entities are column-compatible on everything **except** `issues` and
`recommendations`:
- `ListingQualityCheckEntity` expects these columns to be **`json`** — matches V1. ✅
- `ListingMonitorEntity` expects these columns to be **`TEXT`** — does **not** match
  V1's `json`. ❌

Under `ddl-auto=validate`, Hibernate validates **both** entities against the same
physical table. `ListingMonitorEntity` will report a type mismatch
(`TEXT` mapping vs `json` column) on `issues`/`recommendations` for at least one of
the two mappings — **validation will fail**. Additionally, two `@Entity` classes
mapping the same table with differing column types is a latent data-model defect
regardless of the DB.

### Assessment
- `ListingMonitorEntity` lives in the **`listingops`** module alongside
  `BuyBoxAlertEntity`/`HijackerAlertEntity`/`RepricingRuleEntity` (monitoring concerns),
  while `ListingQualityCheckEntity` lives in the **`review`** module (listing quality
  scoring). The inventory note about a separate `listing_monitors` concept is consistent
  with this: `ListingMonitorEntity` looks like it was intended to be its own
  monitoring table and the `@Table` value is most likely a **copy/paste defect**.
- The column sets are otherwise a perfect overlap, so a `listing_monitors` table would
  be structurally identical to `listing_quality_checks` except `issues`/`recommendations`
  would be `TEXT` instead of `JSON`.

### Recommended fix (NOT applied — needs user/orchestrator decision)
**Option A (recommended): give `ListingMonitorEntity` its own table.**
Change `ListingMonitorEntity` `@Table(name = "listing_quality_checks")` →
`@Table(name = "listing_monitors")` and add a `listing_monitors` table to V1 (same
shape as `listing_quality_checks` but with `issues`/`recommendations` as `TEXT`).
Resolves the collision and the type mismatch.

**Option B: make `ListingMonitorEntity` consistent with the shared table.**
If the two entities are genuinely meant to share one table, change
`ListingMonitorEntity`'s `issues`/`recommendations` to
`@JdbcTypeCode(SqlTypes.JSON)` + `columnDefinition = "json"` (matching
`ListingQualityCheckEntity`) and delete the redundant entity if it adds no behavior.

**Why not auto-fixed:** choosing A vs B changes the data model and could affect
repositories/services that read `ListingMonitorEntity`. This is an entity-side
decision, not a safe mechanical DDL edit, so it is surfaced rather than guessed.
Per task instructions, this is flagged for orchestrator/user attention.

## 5. Four entities with no `columnDefinition` — CHAR(36) alignment (Req 3.1)

Entities `InventoryForecastEntity`, `InventorySnapshotEntity`, `ReplenishmentPlanEntity`,
`ProductProfitDailyEntity` declare `UUID` id/FK fields **without** an explicit
`columnDefinition`. Their V1 tables (`inventory_forecasts`, `inventory_snapshots`,
`replenishment_plans`, `product_profit_daily`) all define id/FK columns as `CHAR(36)`.

- **Tables/columns present and named correctly:** ✅ all id/FK columns
  (`id`, `store_id`, `product_id`, `marketplace_id`, `created_by`, `updated_by`)
  exist as `CHAR(36)` in V1.
- **Residual risk (not a definite failure):** because these four entities omit
  `columnDefinition`, Hibernate maps a bare `UUID` field via the `MySQLDialect`
  default. Modern Hibernate 6 + `MySQLDialect` typically maps `UUID` to a
  binary/`CHAR`-compatible type; whether `validate` accepts `CHAR(36)` depends on the
  exact Hibernate version's type resolution. The other ~79 entities avoid this
  ambiguity by stating `columnDefinition = "char(36)"` explicitly.
- **Recommendation (low-risk, deferred to build verification in task 2.7/build step):**
  if Hibernate `validate` reports a type mismatch on any of these four tables, add
  `columnDefinition = "char(36)"` to their `UUID` id/FK fields to match the rest of the
  codebase. No V1 change is needed — V1 is already `CHAR(36)`. Not changed now because
  it requires a live `validate` run to confirm necessity, and the entity edit (not DDL)
  would be the correct remedy.
